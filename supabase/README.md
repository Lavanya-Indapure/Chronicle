# Database schema

The source of truth for Chronicle's database structure, so it can be
recreated on a fresh Supabase project or moved to another Postgres.

| Path | What it is |
| --- | --- |
| `schema/` | Full snapshot of the live schema (DDL only, no data), generated by `scripts/dump_schema.sh`. |
| `migrations/` | Hand-written changes, applied in filename order. Each is safe to re-run. |

## Refreshing the snapshot

After any schema change (including running a migration), regenerate and commit:

```bash
cp supabase/.env.example supabase/.env   # once; then fill in SUPABASE_DB_URL
bash supabase/scripts/dump_schema.sh
```

Needs Docker. It uses the `postgres:17` image because `pg_dump` must be at
least the server's version (the local PostgreSQL 14 install is too old).

## Recreating the database

On a new **Supabase** project, run in the SQL editor or with `psql`, in order:

1. `schema/extensions.sql`
2. `schema/public.sql`
3. `schema/storage.sql`
4. `migrations/*.sql`. Migrations already in the snapshot are no-ops because they are idempotent.

Then copy the data across separately, for example `pg_dump --data-only --schema=public`.
Storage files must be copied too: the snapshot only covers bucket settings, not the files in them.

## Moving off Supabase (plain Postgres)

The schema references things Supabase provides, which plain Postgres doesn't have:

- **`auth.users`**: `user_id` columns reference it. Create an equivalent `users` table, or drop those foreign keys.
- **`auth.uid()`**: used in RLS policies and column defaults. It needs a replacement that returns the current user's id. A common choice is a function reading a session setting such as `current_setting('app.user_id')`, which the API sets for each request.
- **Roles `anon` / `authenticated`**: named in policies. Create these roles, or rewrite the policies.
- **`storage` schema**: buckets and file policies only make sense with Supabase Storage. Elsewhere, files go to S3 or similar, and the `storage_path` columns keep working as plain keys.

The app also talks to Supabase directly through `supabase_flutter`, so a move
would also need an API layer. The PRD's Express backend is that layer.
